# decisions.md - 설계 결정과 근거 (MVP)

## 0. 전제

과제에 규모, 환경, 수치가 없어서 확실한 기준을 세우기 위해 아래 항목을 전제로 함. 이후 모든 결정은 이 전제에서 결정.

1. 규모: 정합성 중심 업무 시스템. “규모”를 두 축으로 구분.
    1. 한 배 안의 동시성: 소규모. 선원은 20~50, 의료 담당자 1~2, 사용 저빈도 → 동시 사용자 한 자릿수. 비관적 락, 조회 계산의 근거.
    2. 배의 총수: (선사 규모에 따라 수백~수천 척 예상)
    3. 핵심: 락 경합은 배 단위로 격리.
        1. 로트마다 `ship_id`가 있어서 서로 다른 배는 다른 행을 잠금. → 배 수가 늘어도 경합은 각 배 안에서만 발생.
        2. 따라서 비관적 락 판단은 배 총수와 무관하게 유효.
2. 통신: 네트워크를 통해 접근하는 백엔드이며, 연결은 상시 유지된다고 가정.
    1. 오프라인 기록 후 동기화하는 시나리오는 범위에서 제외.
    2. 연결이 유지되더라도 응답 유실, 타임아웃 재시도, 중복 클릭으로 같은 요청이 두 번 도착할 수 있음.
3. 요구사항에 대한 가정.
    1. ‘임박’ 기준 일수는 30일로 가정.
    2. 만료, 임박 판정 기준 시각은 UTC.
4. 구현 범위.
    1. 과제 원안은 설계 문서까지였으나, 실제 구현·배포를 위해 등록·조회 API를 추가.
    2. 과제가 제외한 영역 중 인증·인가와 만료 배치를 구현. 발주·주문, 이벤트 버스 등 그 밖의 비동기 처리, 단위 변환, 선종별 필수 약품 목록은 계속 범위 밖.
    3. 선박 100척과 테스트용 의무사관 계정은 로컬 프로파일에서만 초기 데이터로 둠.
    4. MVP를 먼저 구현·배포한 뒤 기능을 단계적으로 추가. 범위는 requirements 1장을 따름.

## 1. 핵심 결정

### 1. 정책 재고와 물리 재고 분리.

- 맥락: “최소 비치 기준”과 “실제 창고 재고”를 어떻게 모델링?
- 대안:
    1. 한 테이블에 `min_quantity`, `current_quantity` 컬럼으로 통합.
    2. `stock_requirement`(정책)와 `stock_lot`(물리) 별도 테이블.
- 선택: `2`
    1. 실제 재고는 유효기간이 다른 여러 로트로 쪼개져 “수량 하나”로 담을 수 없고 합산으로 계산해야 함.
    2. 통합 시 재고가 0인 약품(로트 미존재)은 행 자체가 없어져 “재고 0 → 부족” 경고를 놓침. 정책은 재고와 무관하게 존재해야 함.
- 트레이드오프: 부족 여부를 판정할 때 (ship, medication)을 조인, 합산. 합산 비용은 부차 결정 5번.

### 2. 로트 잔량을 저장.

- 맥락: 로트의 현재 잔량을 컬럼으로 저장할지, 다른 값으로부터 매번 계산할지?
- 대안:
    1. `remaining_quantity`를 로트 테이블에 컬럼으로 저장하고 차감, 복원 시 갱신한다.
    2. 저장하지 않고 `initial_quantity`에서 allocation 합을 빼 조회할 때마다 계산한다.
- 선택: `1`
- 근거:
    1. 잔량은 실제 차감이 일어날 때 잠금의 대상이자 음수를 막는 `CHECK >= 0`의 대상이므로, 잠글 수 있는 물리 컬럼이 실재해야 함. 계산 방식으로는 잠글 행도 제약을 걸 대상이 없음.
- 트레이드 오프:
    - 저장한 잔량과 allocation이 어긋날 수 있으므로 둘을 같은 트랜잭션에서 함께 갱신해 정합성을 보장.

### 3. 차감 정책은 FEFO에 결정적 정렬을 더함.

- 맥락: 한 번의 사용이 여러 로트에 걸칠 때 어느 로트부터 차감할지?
- 대안:
    1. FIFO: 먼저 입고된 로트부터 차감.
    2. LIFO: 나중에 입고된 로트부터 차감.
    3. FEFO: 유효기한이 임박한 로트부터 차감.
    4. 수량 기반: 잔량이 적거나 많은 로트부터 차감.
- 선택: `3`, 동점 시 `received_at → id`순으로 정렬.
- 근거:
    1. 유효기한 관리가 핵심인 의약품 도메인에서, FIFO는 입고 순서가 만료 순서와 달라 임박한 로트를 방치할 수 있고, LIFO는 오래된 재고를 남겨 폐기를 늘리며, 수량 기반은 유효기한을 무시. FEFO만이 만료 손실을 최소화하며 병원, 약국 물류의 표준.
    2. 유효기간이 같은 로트는 `received_at`, 그다음 `id` 순으로 처리해 순서를 유일하게 확정. 그래야 실행 결과가 매번 같아 재현과 취소가 꼬이지 않음.

### 4. 동시성은 비관적 락과 CHECK 제약으로 막음.

- 맥락: 여러 사관이 동시에 사용을 기록할 때 이중 차감과 음수 재고를 막아야 했음.
- 대안:
    1. 낙관적 락
    2. 비관적 락
    3. DB 제약만
- 선택: `2+3`
- 근거:
    1. 경합이 배 단위로 격리되므로 실제 충돌은 한 배 안에서만 드물게 일어남. 따라서 비관적 락의 블로킹 비용은 사실상 0이고, 재시도 관리가 필요한 낙관적 락보다 구현이 단순.
    2. 판단의 핵심은 조회량이 아니라 쓰기 충돌 빈도이며, 충돌 확률이 낮더라도 한 번이라도 겹치면 재고가 깨지므로 방어 자체는 필수.
    3. 한 번의 사용이 여러 로트를 잠그므로 데드락을 막기 위해 락 획득 순서를 `id` 오름차순으로 고정.
- 유보:
    - 한 배 안 경합이 심한 환경, 의료진이 여럿인 대형 선박으로 확장되면 낙관적 락 병행을 검토.

### 5. 멱등성은 Idempotency Key로 보장.

- 맥락: 서버는 처리했지만 응답이 유실되거나 늦으면 클라이언트는 성공 여부를 알 수 없어 재요청. 중복 클릭도 같은 결과. 재고 차감은 두 번 실행되면 안 되는 작업이므로 서버가 스스로 중복을 막아야 함.
- 대안:
    1. Idempotency Key — 클라이언트가 요청마다 보내는 고유 키로 인바운드 중복을 차단.
    2. 그 밖에 자연 키, 클라이언트 측 방어, 조건부 업데이트, 사후 취소.
- 선택: `1`
- 근거:
    1. 자연 키는 정당한 반복 사용을 오판하고, 클라이언트 측 방어는 서버가 스스로를 보호하지 못하며, 조건부 업데이트는 재시도가 아니라 동시성을 막는 도구이고, 사후 취소는 예방이 아님.
    2. 클라이언트가 보내는 키를 usage_record에 컬럼으로 흡수하고 UNIQUE(user_id, idempotency_key)를 걸음. 상태 변경 종류가 적어 별도 키 테이블은 과하다고 봄. 처리 전 확인과 UNIQUE 제약으로 이중 방어하며, 취소는 특정 usage_id를 겨냥하므로 status 확인만으로 자연히 멱등.
    3. 같은 키 동시 요청: 둘 다 처리 전 확인을 통과하면 늦은 쪽이 INSERT에서 UNIQUE 위반. PostgreSQL은 위반 후 트랜잭션을 중단시키므로, 롤백한 뒤 새 트랜잭션에서 기존 기록을 조회해 200으로 반환. 롤백으로 늦은 쪽의 차감도 함께 취소되어 이중 차감이 없음.
    4. 같은 키에 다른 내용: 기존 기록의 (ship_id, medication_id, total_quantity)와 비교해 다르면 409 `IDEMPOTENCY_KEY_REUSED`. 비교할 값이 이미 usage_record에 있으므로 요청 해시 컬럼은 두지 않음. 키를 잘못 재사용한 요청에 기존 결과를 돌려주면 클라이언트가 다른 요청이 성공했다고 오해하기 때문.
    5. 헤더가 없거나 비었으면 400. 키 없이 받으면 재시도 방어가 사라지므로 선택값으로 두지 않음.

### 6. 취소는 삭제가 아니라 상태 전이와 감사 메타로 처리.

- 맥락: 잘못 기록한 사용을 취소할 때 어떻게 남길지?
- 대안:
    1. 상태 컬럼만 두어 취소 여부를 표시.
    2. 상태에 취소 메타(시각·취소자·사유)를 더함.
    3. 취소를 별도 보상 이벤트 행으로 남김.
- 선택: `2`
- 근거:
    1. 원본을 삭제하면 실수했다가 취소한 흔적까지 사라져 감사 추적이 깨짐. status를 전이해 유효성을 나타내고 cancelled_at·cancelled_by·cancel_reason으로 누가 언제 왜 취소했는지를 보존. 3안의 이벤트 테이블 복잡도는 피함.
    2. 복원은 allocation 기록대로 원래 로트에 정확히 되돌리며, 그 로트가 만료·폐기되었더라도 그대로 복원하고 가용 여부는 조회 시점에 판정. 복원을 거부하면 정당한 취소를 막고 재고를 왜곡하기 때문.
- 트레이드오프: 이중 취소가 가능하므로 usage_record를 FOR UPDATE로 잠그고 status를 확인해, 이미 취소된 건은 다시 처리하지 않음.

### 7. 역할은 관리자와 의무사관으로 나누고, 의무사관은 소속 선박에 묶음.

- 맥락: 과제는 인증·인가를 제외하고 `X-User-Id`로 사용만 식별. 실제로 운영하려면 누가 어떤 기능을 쓸 수 있는지 정해야 함.
- 선택:
    1. 관리자: 계정, 약품 카탈로그, 선박, 비치 기준을 관리하고 모든 선박의 재고를 조회.
    2. 의무사관: 소속 선박에서 입고, 사용, 취소를 하고 그 선박의 재고와 비치 기준을 조회. 다른 선박의 비치 기준을 볼 업무가 없으므로 재고 현황과 같이 소속 선박으로 제한.
    3. 취소·정정은 기록한 본인만 할 수 있음.
    4. 입고는 약품이 실제로 배에 실리는 곳에서 일어나므로 의무사관이 함.
- 근거:
- 유보: 의무사관이 하선했거나 연락이 안 될 때 관리자가 잘못된 기록을 취소할 수 있게 할지는 나중에 정함.

### 8. 로그인은 세션으로 시작하고 나중에 JWT로 전환.

- 맥락: 로그인 상태를 서버 세션으로 유지할지, 토큰으로 유지할지 정해야 함.
- 대안:
    1. 세션
    2. JWT
- 선택: `1`, 이후 JWT 전환.
- 근거: 이후 단계의 화면을 Thymeleaf로 같은 서버에서 그리므로 세션이 단순. 화면을 React로 분리할 때 JWT로 전환.
- CSRF: MVP는 API만 있어 CSRF 보호를 끄고 세션 쿠키를 `HttpOnly`, `SameSite=Lax`로 발급. `SameSite=Lax`는 다른 사이트에서 오는 POST에 쿠키를 싣지 않으므로 MVP 범위에서는 충분. 화면(Thymeleaf) 단계에서 폼이 생기면 CSRF 보호를 켬.

### 9. 사용자 기록은 사용자 테이블의 id를 참조.

- 맥락: `usage_record.user_id`, `cancelled_by`는 `X-User-Id` 헤더 문자열을 저장. 헤더를 쓰던 때는 사용자 테이블이 없어 참조할 대상이 없었음. 입고는 누가 했는지 기록하지 않았음.
- 선택: `tb_user(id)`를 참조하는 FK로 바꿈. 입고한 의무사관도 `tb_stock_lot.received_by`로 기록해 사용·취소·입고 모두 “누가”를 남김.
- 근거: 사용자 테이블이 생겼으므로 존재하지 않는 사용자가 기록되지 않게 DB가 보장.
- 트레이드오프: 기록이 남은 사용자는 삭제할 수 없음. 계정 정리 방식은 미해결에 둠.

## 2. 부차 결정

### 1. 재고 부족 처리: 전부 거부 후 가용량 안내.

- 가용 재고가 요청량보다 적으면 부분 차감 없이 409로 거부하고 응답에 현재 가용 수량을 담아서 응답.

### 2. 만료 판정은 조회 시 계산하고, 배치는 부가 작업만.

- 차감·재고 현황의 만료 판정은 `expiry_date < 오늘(UTC)` 비교로 조회할 때.
- 배치는 판정에 쓰이지 않는 부가 작업만. 배치가 늦거나 실패해도 만료 로트가 차감되는 일이 없게 하기 위함. 판정까지 배치가 찍은 상태값에 맡기면, 자정(UTC)이 지나고 배치가 돌기 전까지 만료 로트가 차감될 수 있음.
- 배치는 spring batch로 작성하고 스케줄러로 실행. 서버는 한 대를 전제로 하므로 중복 실행 방지 잠금은 두지 않음.
- 구현은 MVP 이후 단계에서.

### 3. 유효기한 경계: 당일까지 유효, UTC 기준.

- `expiry_date >= 오늘`로 판정하며, 선박이 타임존을 넘나들어도 일관되도록 UTC를 기준으로 한다.

### 4. 비치 기준 없는 약품.

- 사용은 기준과 무관하게 로트만 참조하므로 가능.
- 재고 현황은 해당 배의 (비치 기준이 있는 약품 ∪ 로트가 있는 약품)을 대상으로 한다. 한쪽에서만 LEFT JOIN하면 둘 중 하나를 놓치기 때문.
    - requirement 기준 LEFT JOIN만 하면 기준 없이 재고만 있는 약품이 빠짐.
    - lot 기준 LEFT JOIN만 하면 기준은 있는데 로트가 없는 약품이 빠져, 핵심 결정 1번의 “재고 0 → 부족” 경고를 놓침.
- 기준이 없는 약품은 `requirementSet:false`, `minQuantity:null`, `shortage:null`로 표시. 기준이 없으면 부족을 판정할 수 없으므로 `false`가 아니라 `null`.

### 5. 가용 재고는 캐시 없이 매번 합산.

- “로트 하나의 잔량”은 저장하지만, “배 전체의 그 약품 재고”는 저장하지 않음.
- 합산할 때 전체 로트가 아니라 해당 배의 해당 약품 로트만 더하므로 배가 아무리 많아도 한 번의 합산 비용은 작다.

### 6. FEFO 인덱스.

- 핵심 인덱스는 `stock_lot(ship_id, medication_id, expiry_date, received_at, id)`로 FEFO 조회 전용이며 등호 필터를 앞에, 범위, 정렬을 뒤에 둔다.

### 7. 입고 시각은 클라이언트가 필수로 입력.

- 의무사관은 물품을 받은 뒤 나중에 등록할 수 있어 실제 입고 시각과 등록 시각이 다름. 실제 시각을 남기는 편이 기록으로서 정확하고, 등록 시각은 `created_at`이 따로 남으므로 두 값이 섞이지 않음.
- 필수로 둠. 생략 시 서버 시각으로 채우면 실제 입고 시각과 등록 시각이 구분 없이 섞임.
- 날짜가 아니라 시각(TIMESTAMPTZ)으로 받음. 날짜만 받으면 같은 날 입고한 로트가 다시 동점이 되어 `id`로 순서가 정해짐.
- 미래 시각만 막고 과거 하한은 두지 않음. 과거로 적어 차감 순서를 바꿀 여지는 남지만 유효기한이 같은 로트 사이의 순서만 바뀌어 영향이 작고, 하한 규칙은 검증과 테스트만 늘림.
- (이전 안) 서버 기록: 검증이 필요 없고 조작 여지가 없지만 실제 입고 시각과 어긋남.

### 8. 권한 판정 순서.

- 로그인(401) → 역할(403) → 소속 선박(403) → 형식 검증(400) → 대상 존재(404) → 규칙 검증(400) → 비즈니스 규칙(409).
- 의무사관이 존재하지 않는 선박으로 요청해도 403. 소속 선박 판정은 세션의 shipId와 비교만 하면 되어 DB 조회 없이 먼저 끝낼 수 있고, 다른 선박의 존재 여부를 드러내지 않음.
- 형식 검증을 대상 존재보다 앞에 둠. `@Valid`는 컨트롤러 진입 전에 실행되어 서비스의 404보다 먼저 나감. 권한을 통과한 뒤라 400이 먼저 나가도 다른 선박 정보가 드러나지 않음.
- (이전 안) 대상 존재(404) → 입력 검증(400): 지키려면 형식 검증을 전부 서비스로 옮겨야 해서 공통 예외 처리의 `@Valid`, `fieldErrors` 구조를 쓸 수 없음.

### 9. 같은 로트 번호 입고는 409.

- `uq_lot(ship_id, medication_id, lot_number)` 위반은 409 `DUPLICATE_LOT`. 같은 로트를 추가로 받는 경우는 MVP에서 다루지 않고, 기존 로트의 수량을 늘리는 대신 거부해 `initial_quantity`가 입고 1회의 수량으로 유지되게 함.

### 10. 로그인·로그아웃은 컨트롤러에서 처리.

- 로그인: `formLogin`은 기본적으로 폼 파라미터를 받아, JSON 요청을 받으려면 필터를 직접 만들어야 함. 컨트롤러는 `@Valid`와 공통 에러 형식을 그대로 쓸 수 있음.
- 로그아웃: `LogoutFilter`는 권한 검사보다 먼저 실행되어 미로그인 요청도 200이 됨. 컨트롤러로 처리하면 `anyRequest().authenticated()`가 적용되어 분기 코드 없이 401이 됨.
- 트레이드오프: 필터 방식에서 Security가 해 주던 세션 ID 교체와 `SecurityContext` 저장을 직접 해야 함.

### 11. 로그인 ID 중복은 409.

- 형식 오류가 아니라 기존 데이터와의 충돌이므로 400이 아니라 409 `DUPLICATE_LOGIN_ID`. 부차 9번의 `DUPLICATE_LOT`과 같은 기준.
- 처리하지 않으면 제약 위반이 500으로 나가 클라이언트가 원인을 알 수 없음.
- 동시 요청은 잠금이 아니라 유니크 제약으로 막음. 새 계정은 아직 행이 없어 `SELECT ... FOR UPDATE`로 잠글 대상이 없고, 사전 조회만으로는 두 요청이 함께 통과할 수 있음. 이미 있는 행을 바꾸는 재고 차감과 다른 점.
- 사전 조회는 흔한 중복을 일찍 거절하고 BCrypt 해시 비용을 아끼려고 유지함. 실제 중복을 막는 것은 `uq_user_login`.
- 대안: `SERIALIZABLE`은 재시도 처리가 추가로 필요하고, 분산·애플리케이션 잠금은 계정 등록에 과함. `INSERT ... ON CONFLICT`는 이 등록 하나만 네이티브 쿼리로 나뉨.

### 12. 입력 길이는 DDL에 맞추고 비밀번호는 8~20자, 영문·숫자·특수문자 조합.

- 길이 초과를 검증하지 않으면 DB 오류가 500으로 나감. 잘못된 입력이므로 형식 검증에서 400으로 거부.
- 최소 8자: 정책이 없으면 1자 비밀번호도 등록됨.
- 최대 20자, ASCII 문자만: BCrypt의 입력 상한은 72바이트이고 넘으면 해시 단계에서 예외가 남. 이 규칙이면 상한을 넘을 수 없어 바이트 검사가 필요 없음.
- 대가: 20자보다 긴 비밀번호와 허용 목록 밖의 문자는 거부됨.

### 13. 단순 목록은 JPA와 페이지네이션, MyBatis는 복잡한 조회에만.

- 맥락: 처음에는 쓰기를 JPA, 조회를 MyBatis로 나눴으나 단순 목록까지 매퍼와 SQL을 두는 것은 얻는 것이 적음.
- 선택: 단순 목록은 JPA로 조회하고, MyBatis는 재고 현황처럼 SQL의 장점이 드러나는 집계와 복잡한 조회에만 씀.
- 배가 수백~수천 척까지 늘 수 있어(전제 1번) 목록을 한 번에 전부 응답하지 않고 페이지 단위로 응답. 비치 기준 목록은 크기가 약품 수로 제한되지만 응답 형식을 통일하기 위해 함께 적용.
- 형식 검증과 일관되게 범위를 벗어난 `page`, `size`는 보정하지 않고 400.
- `page` 상한은 21474836. `page × size`가 int 범위를 넘으면 Spring Data가 예외를 던져 500이 되므로, 최대 `size` 100을 기준으로 막음. 빈 페이지로 응답하는 안은 목록마다 공통 처리가 필요한데, 이렇게 큰 값은 정상 요청이 아니므로 거부로 충분함.
- 유보: 이후 커서 방식으로 전환. 전환하면 `page`, `totalElements`, `totalPages`는 쓰지 않음(3장).

### 14. 비치 기준 동시 신규 등록은 재시도.

- 맥락: 신규 요청 두 개가 겹치면 늦은 쪽이 `uq_requirement` 위반. 데이터는 깨지지 않지만 정상 요청이 500을 받음.
- 대안:
    1. 위반 시 새 트랜잭션에서 수정.
    2. `INSERT ... ON CONFLICT`.
    3. 500을 허용하고 클라이언트가 재시도.
- 선택: `1`
- 근거: 쓰기를 JPA로 유지하고 200과 201을 그대로 구분할 수 있음. 2안은 네이티브 SQL이 필요하고 신규와 수정을 구분하기 번거로움. 3안은 정상 요청에 서버 오류를 돌려줌.

### 15. API 경로는 `/api`로 시작.

- 로그인을 포함한 모든 API에 적용.
- 이후 단계의 화면(Thymeleaf)이 같은 서버에 생기므로 API 경로와 화면 경로를 구분할 수 있음.

## 3. 미해결, 유보

- “임박” 기준 일수(현재 30일 가정)를 실제 운용에 맞게 수정.
- 대규모, 분산으로 확장할 경우 낙관적 락 병행, UUIDv7, 파티셔닝과 캐시 도입 고려.
- 감사 로그의 CSV, PDF export와 이력은 append-only로 보존해 나중에 확장할 수 있도록.
- 계정 정리: 기록이 남은 사용자는 삭제할 수 없음(핵심 결정 9번). 하선한 의무사관의 로그인을 막을 비활성화(`enabled`) 도입 여부.
- MVP 이후 단계:
    - 정정: 과제 당시에는 “취소 후 재기록”으로 결정. 취소와 같이 본인 기록만 정정할 수 있음. 구체적인 처리 방식은 정정 구현 시 확정.
    - 로트 폐기: 의무사관.
    - 사용 이력 조회.
    - 화면.
    - JWT 전환.
    - 만료 배치: 배치가 맡은 작업(만료 로트 상태 표시, 만료·임박 알림, 만료 로트 자동 폐기 등)은 구현 시 정함. 서버를 여러 대로 늘리면 중복 실행 방지 잠금이 필요.
    - 목록 커서 전환: 대상과 시점은 전환할 때 정함.
